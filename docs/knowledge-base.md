# База знаний проекта «Кассовый прогноз» (хакатон ЦентрИнвест, осень 2026)

Документ описывает то, что **реально реализовано** в репозитории, и отличия от целевой архитектуры (`architecture.md`). Состояние на ветку `testing`.

## 1. Что за проект

Сервис для малого бизнеса: принимает банковскую выписку, категоризирует операции, находит регулярные платежи, строит прогноз остатка по дням (7–90 дней, по умолчанию 30) и оценивает риск кассового разрыва (дата, сумма, вероятность). Есть сценарии «что если», план-факт, ручной ввод ожидаемых платежей, проверка качества (backtest).

Источники требований:
- `docs/task/ЦентрИнвест1.pdf` — условия кейса (обязательный минимум и «задачи со звёздочкой»).
- `docs/architecture.md` — целевая архитектура (спецификация, не отчёт о реализации).
- `docs/design.md` — структура интерфейса и визуальный стиль Fintech Minimal.
- `docs/forecast_evaluation.md` — оценка качества прогноза на датасете.

## 3. Как устроен код

```
backend/api/        Rust (Axum, rusqlite): публичный API :3000 + внутренний :3100, финансовое ядро
  src/main.rs        маршруты, middleware (CSRF по Origin, заголовки, request id, лог без тел)
  src/http.rs        обработчики, авторизация, импорт, события, прогнозы, сценарии, план-факт
  src/forecast.rs    регулярности, остаточный поток, траектории, риск, backtest
  src/db.rs          схема SQLite
  src/bin/eval.rs    оценка на всём датасете (cargo run --release --bin eval)
backend/services/auth/     Python FastAPI :8001 — пользователи, сессии (scrypt, sha256 токена, lockout)
backend/services/parser/   Python FastAPI :8002 — разбор CSV/XLSX, категоризация
backend/services/tests/    pytest
web/               React + TypeScript + Vite, ECharts, Inter (локально)
infra/ (docker/, docker-compose.yml, Makefile, scripts/)   контейнеры и Caddy gateway (не проверялись: Docker не установлен на машине разработки)
infra/scripts/dev.sh     запуск без Docker; infra/scripts/gen_statement.py — синтетическая выписка
docs/              документы
data/              в .gitignore: dataset/ (из data/raw/*.zip), run/ (БД и логи локального запуска), eval/
```

Поток данных: браузер → (Caddy в Docker) → Rust API → Python `auth` (сессия) / `parser` (разбор файла) → SQLite. Прогноз считается в Rust синхронно в `spawn_blocking`.

### Что изменено относительно `architecture.md`
- SQLite вместо PostgreSQL; нет RLS, очереди заданий (`jobs`), SSE, Idempotency-Key.
- Нет Python ML-сервиса: категоризация — в парсере, прогноз — в Rust.
- Нет OpenAPI-контрактов, Podman/Ansible, Cosign/SBOM, Prometheus.
- Изоляция компаний — проверкой `company_id` с принципалом (чужая компания → 404), одна компания на пользователя.
- Консультант без LLM и без отдельного advisor-сервиса.

## 4. Запуск

Без Docker (проверено):
```
infra/scripts/dev.sh        # сборка web и api, запуск auth, parser, api; http://localhost:3000
infra/scripts/dev.sh stop
```
Демо-логин: `demo@example.com` / `demo12345` (`DEMO_SEED=1`). Состояние локального запуска — `data/run/` (БД, логи, pid).
Не запускайте `pkill -f` с текстом, который есть в вашей же команде: он убивает собственную оболочку; используйте `pkill -x api` и `pkill -x uvicorn`.

Docker (написано, но не собиралось): `make -C infra up` → http://localhost:3000, наружу смотрит только Caddy.

Тесты:
```
cd backend/api && RUSTUP_TOOLCHAIN=stable cargo test       # 13 тестов
cd backend/services && uv run pytest -q                           # 63 теста
cd web && npx tsc --noEmit && npm run build
```
Оценка на датасете: `cd backend/api && cargo run --release --bin eval -- --compare --csv` (запускать из корня репозитория, ~2 с на все 150 компаний).

Переменные окружения API: `PUBLIC_ADDR`, `INTERNAL_ADDR`, `AUTH_URL`, `PARSER_URL`, `DB_PATH`, `WEB_DIR`, `COOKIE_SECURE`. Для auth: `AUTH_DB`, `DEMO_SEED`.

## 5. Публичный API (все под cookie `session`, кроме auth)

```
POST /api/v1/auth/register|login|logout    GET /api/v1/auth/me
PATCH /api/v1/companies/{cid}                         название юрлица
POST|GET /…/imports   GET /…/imports/{id}   POST /…/imports/{id}/confirm
GET /…/transactions?limit&offset&category&direction&q&sort&order    PATCH /…/transactions/{id}/category
GET|POST /…/expected-events   DELETE /…/expected-events/{id}   POST /…/expected-events/tax-calendar
POST /…/forecasts {horizon_days}   GET /…/forecasts/latest   GET /…/forecasts/{run_id}
POST /…/scenarios   GET /…/backtest   GET /…/plan-fact?days=
Внутренний :3100: /internal/v1/health, /internal/v1/companies/{cid}/summary
```
Правила: суммы — копейки, в JSON десятичными строками (BigInt на фронте); ошибки `{"error":{"code","message"}}`; 422 для недопустимых значений; 409 для дубля файла; 404 для чужой компании.

## 6. Данные и импорт

Хранилище (SQLite): `companies`, `imports` (staging payload до подтверждения), `transactions` (UNIQUE по `dedup_key`), `expected_events`, `forecast_runs` (результат JSON, `data_revision`), `audit_events`.

Импорт: загрузка → разбор парсером → preview (статистика, ошибки без содержимого строк, дубли, категории) → подтверждение (транзакция, `INSERT OR IGNORE` по ключу «дата|сумма|ИНН|назначение|n-е вхождение») → `data_revision+1` → прогноз становится «устаревшим» (`stale`).
Лимиты: 25 МБ, 200 000 строк, форматы CSV (UTF-8/BOM или cp1251; разделитель определяется) и XLSX без исполнения формул.

Парсер: гибкие алиасы колонок, суммы в копейках через Decimal, направление по колонке/знаку/дебет-кредит. Остаток: режим `eod` (остаток на конец дня, одинаков для всех операций дня) или `running` (по строкам); сверка по дням, пропуски периодов (>5 дней), подозрения на дубли. Новая категория: `refunds`. Категории: revenue, other_income, suppliers, payroll, rent, taxes, loans, utilities, bank_fees, marketing, transfers, refunds, other_expense. Внутренние переводы (`transfers`) исключаются из прогноза.

Датасет (`data/dataset/`, README внутри): 150 синтетических компаний, 01.10.2024–30.09.2026, ≈222 тыс. операций, только рабочие дни, остаток EOD, пропуски до 52 дней, овердрафт, ~21 дубль, разные отрасли и режимы налогов. ИНН — строки с ведущими нулями. 142 компании пригодны для backtest.

## 7. Прогнозная модель (`forecast.rs`, `recurring-bootstrap/2`)

Баланс траектории: `balance(d) = balance(d−1) + регулярные/ожидаемые события + остаточный поток`.

1. **Регулярности.** Группировка по ИНН/контрагенту (+ вторичный ключ по началу назначения). Месячные (1–2 раза в месяц, ≥3 «полных» месяца, ≥75 % совпадений) и недельные. Для каждой: якорные дни, суммы (последние 6), разброс дат. «Протухшие» (давно не было) отбрасываются.
2. **Остаточный поток** — операции вне регулярностей: окно 120 дней, блочный bootstrap по неделям с выравниванием по дню недели, выходные = 0, дни пропусков выписки исключаются.
3. **События.** Ожидаемое событие (ручное/счёт/налог) заменяет похожую регулярность (±7 дней, тот же контрагент или сумма ±30 %), чтобы не считать дважды. Просроченные поступления сдвигаются, просроченные расходы — на завтра.
4. **Календарь.** Российские рабочие дни 2024–2027: платежи с якорем на выходной сдвигаются на следующий рабочий день.
5. **Траектории.** 1000 путей, фиксированный seed (воспроизводимо); дрейф статистической части гасится, баланс тянется к медиане 120 дней (1,5 % за рабочий день) — единственное, что дало выигрыш над наивным прогнозом на 30 дней.
6. **Риск.** Из траекторий: вероятность хотя бы одного минуса, медиана первой даты разрыва, дата, к которой накопленная вероятность ≥10 %, типичный дефицит, 90-й перцентиль максимального дефицита; уровни none/low/medium/high по порогам 5/20/50 %. Причины — крупнейшие плановые списания до даты разрыва.
7. **Сценарии** (один seed с базой): задержка платежа контрагента (клиент — поступления; явно названный контрагент — любое направление), падение выручки %, рост постоянных расходов %, внеплановый расход, дополнительное поступление.
8. **План-факт:** шаблоны регулярностей и события сопоставляются с фактом (±5 дней, сумма ±15 % → оплачено, иначе отклонение; нет → не пришло/ожидается).
9. **Качество данных:** `quality.level` good/medium/low (история <60/<180 дней), заметки о пропусках, овердрафте, устаревшей выписке.

Известные допущения: прогноз строится от даты последней операции в выписке (без «моста» до сегодняшнего дня); одна валюта RUB.

## 8. Интерфейс (`web/`)

Разделы (маршруты): Обзор `/dashboard`, Прогноз `/forecast`, Операции `/transactions`, Платежи и обязательства `/obligations`, Сценарии `/scenarios`, План-факт `/plan-vs-actual`, AI-консультант `/assistant`, Настройки `/settings`. Каркас: Sidebar, Header (организация, уведомления из предупреждений, профиль), общий контекст `ctx.tsx` (последний прогноз, `refresh`, `recalc`, импорт-модалка).
Дизайн-токены в `styles.css` (зелёный `#176B45`, фон `#F7F9F7`, предупреждения `#D97706`, риск `#DC5252`); цвет всегда с текстовым статусом. Вход/регистрация: название юрлица, повтор пароля, значок глаза у пароля. Суммы форматируются через BigInt (`api.ts: rub`). Страницы пока не проверялись в браузере вручную.

## 9. Результаты оценки (142 компании, rolling-origin, шаг 14 дней)

Нормированная ошибка (MAE / медианный недельный оборот), mean:

| Горизонт | Модель | «остаток не меняется» | Тренд | Покрытие p10–p90 |
|---|---|---|---|---|
| 7 дн. | 38,1 % | 39,9 % | 47,2 % | 71,6 % |
| 14 дн. | 51,4 % | 53,8 % | 69,9 % | 76,1 % |
| 30 дн. | 65,5 % | 68,6 % | 110,5 % | 81,4 % |

- Модель лучше обоих базовых подходов у ~78 % компаний, но по доле точек только ~46–50 %: выигрыш над наивным прогнозом небольшой (3–5 % на 30 дней).
- Тревога «P(разрыв) ≥ 0,5»: precision 0,22, recall 0,80 (229 реальных окон разрыва). При пороге 0,9: precision 0,75, recall 0,66.
- **Вероятности плохо откалиброваны:** прогнозы 0,2–0,8 сбываются в 4–12 % случаев; ≥0,95 — в 85 %. Причина, вероятно, в поведении владельцев (пополнения и вывод средств удерживают счёт около нуля). В интерфейсе это названо «модельной оценкой».
- Скорость: один прогноз на 222 тыс. операций ≈ 0,6 с (release).

## 10. Безопасность

- Пароли: scrypt; токен сессии хранится как sha256; блокировка после 5 неудачных входов (5 минут); одинаковая работа для существующего/несуществующего пользователя.
- Cookie `session`: HttpOnly, SameSite=Strict, Secure при `COOKIE_SECURE=1`. Для изменяющих запросов Origin сверяется с Host.
- Заголовки: CSP, nosniff, frame deny, no-referrer, Cache-Control no-store на API.
- В логах нет тел запросов, назначений платежей, паролей; ошибки парсера содержат только номер строки и код.
- Аудит в таблице `audit_events` (импорт, события, прогнозы, сценарии, смена названия).
- Внутренний API на отдельном порту, наружу не публикуется; Caddy отдаёт 404 на `/internal/*`.
- Не сделано: RLS, rate-limit на остальные эндпоинты, OIDC, шифрование БД.

## 11. Известные ограничения и идеи

- Калибровка вероятности разрыва; ширина интервалов на 7–14 днях.
- Налоговый календарь: добавить авансы УСН, НДС по кварталам, расчёт ЕНП из истории.
- Интеграции: график кредита (CSV), зарплатный проект, проверка контрагента по открытым реестрам, 1С/ЭДО.
- Частичное обновление прогноза без пересчёта; «мост» от даты выписки до сегодня.
- Настройки отображения сохраняются в браузере, но нигде не применяются.
- Docker/Caddy: файлы написаны и проверены только на валидность compose; сборка образов не выполнялась.
- AI-консультант: подключение LLM — отдельный модуль; сейчас детерминированные ответы.
- Схема архитектуры для презентации.

## 12. Презентация: чем подкрепить критерии оценки

1. Качество прогноза — §7 и §9, `docs/forecast_evaluation.md` (сравнение подходов, честные метрики, калибровка).
2. Выявление разрывов — страница «Прогноз», предупреждения с причинами, backtest тревог.
3. Дополнительные источники — ручные события, налоговый календарь, счета/договоры как источники, импорт; слабое место — внешние интеграции.
4. Техническое качество — тесты (13 + 63), граничные случаи (пропуски, овердрафт, короткая история, дубли), безопасность.
5. Демонстрация — демо-компания (`infra/scripts/gen_statement.py`) и реальные выписки из датасета (C001, C004 с пропусками и овердрафтом).
