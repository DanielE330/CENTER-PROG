# Команда компании: роли, сотрудники, приглашения

Одна модель на весь сервис. Состав и роли хранит **ledger** (`company_members`, пользователь состоит ровно в одной компании), права проверяет **api** при каждом запросе (смена роли, удаление и блокировка действуют сразу), приглашения-ссылки выдаёт **auth**. Подробности прав по маршрутам и внутренние контракты — в [roles.md](roles.md), панель оператора и блокировка компании — в [backoffice.md](backoffice.md).

## Роли

В коде и API роли называются `director | admin | editor | viewer`, в интерфейсе — «Владелец», «Администратор», «Аналитик», «Наблюдатель». Прежние названия (`owner | admin | analyst | observer` из версии с составом в auth, `Директор / Редактирование / Чтение` из версии с ролями только в ledger) — те же роли:

| API | Интерфейс | Было | Права |
|---|---|---|---|
| `director` | Владелец | director · owner | всё; передаёт владение; назначает, понижает и удаляет администраторов; способы своего входа (email, ЭЦП), токены других сотрудников |
| `admin` | Администратор | admin | команда (аналитики и наблюдатели), приглашения, название компании, настройки Telegram, отделы и политики, согласие на ИИ, журнал действий, плюс всё, что у аналитика |
| `editor` | Аналитик | editor · analyst | чтение и изменение данных: импорт выписок, платежи, категории, налоговый календарь, синхронизация, цели недели и ретро |
| `viewer` | Наблюдатель | viewer · observer | только чтение и вычисляющие запросы (прогнозы, сценарии, вопрос консультанту), своя привязка Telegram |

Права в `/auth/me` и ответе входа: `permissions: {read, edit, admin, manage}`. `admin` — владелец и администратор, `manage` — только владелец. Роль читается при каждом запросе: ни кэша, ни перезапуска не нужно.

## Два способа добавить человека

1. **С паролем** (`POST /api/v1/members {email, role, password | generate}`): администратор или владелец создаёт учётную запись; пароль (заданный или сгенерированный, виден один раз) нужно сменить при первом входе. Сотрудник входит по email и паролю.
2. **По ссылке** (`POST /api/v1/team/invites {role, email?}`): одноразовая ссылка `/?invite=<код>` на 7 дней (в базе только sha256 кода). Приглашённый входит или регистрируется и подтверждает вступление. Если указан email, принять приглашение сможет только пользователь с этим адресом, а письмо уйдёт через почтовый сервис `notify` (50 писем в час на компанию; если почта недоступна, сайт показывает ссылку). Приглашение «с паролем» тоже приходит письмом: ссылка «задать пароль» на 72 часа, пароль остаётся запасным вариантом.

Администратора назначает (в том числе приглашением) и убирает только владелец; администратор управляет аналитиками и наблюдателями. Участников не больше 50 на компанию.

**Вступление по ссылке:** у приглашённого уже есть своя пустая компания, которая создаётся при первом входе. Она убирается, и человек переезжает в компанию пригласившего. Если в его компании есть данные или команда, принять приглашение нельзя (`has_team`), а ссылка остаётся рабочей: сначала проверка приглашения, затем запись в ledger, и только потом код расходуется.

**Выход из команды** (`POST /api/v1/team/leave`): участник получает новую собственную компанию. Владелец выйти не может, пока не передаст владение.

## Передача владения

`POST /api/v1/team/transfer {user_id}` (только владелец): выбранный участник становится владельцем, прежний — администратором, id компании не меняется, поэтому данные, токены и подключённые чаты остаются на месте. Telegram-роли обоих обновляются автоматически. Бывший владелец, которого потом удалили, прав не возвращает: при входе он получит новую пустую компанию.

## Миграция из прежней версии

Если база создавалась версией, где состав команды хранил auth (`memberships(user_id, tenant_id, role)`), при старте api разово переносит команды в ledger: администратор → `admin`, аналитик → `editor`, наблюдатель → `viewer`, владельцу-не-создателю передаётся владение. Миграция идемпотентна, после успеха старая таблица откладывается (`memberships_migrated`), чтобы позже удалённых из команды никто не воскресил. Старые приглашения (они указывали на владельца, а не на компанию) аннулируются; ссылки нужно выпустить заново. База ledger с тремя ролями пересобирается автоматически (добавляется `admin`), существующие участники сохраняются.

## Журнал действий

Страница «Журнал» (владелец и администратор, `GET /api/v1/team/activity?limit&offset&q`): приглашения, смены ролей, сотрудники, передача владения, цели (в том числе отметки в Telegram как `tg:<id>`), настройки уведомлений, импорты, платежи, прогнозы, токены. Записи лежат на диске в `audit_events` ledger (том `ledger-data`), автоматически не удаляются; имена участников подставляет api (email или название сертификата ЭЦП). В журнал пишутся только состоявшиеся действия. Экспорт: «Скачать CSV» (`.../activity/export?q=`, до 20 000 строк, UTF-8 с BOM, `;`, значения-формулы экранируются апострофом).

## Блокировка компании и Telegram

Заблокированная оператором компания не получает ничего: вход и все запросы людей и API-токенов — `403 company_banned`; при включённой 2FA билет второго шага не выдаётся, а выданный до блокировки не даёт сессию после верного кода; ссылка привязки Telegram закрыта, а `notifier` перестаёт рассылать алерты и отчёты и молчит в чатах (одно объяснение «компания заблокирована», привязать новый чат нельзя). Разблокировка возвращает всё в течение минуты (кэш статуса в `notifier`).

## Связь с Telegram

Любая роль привязывает свой Telegram (`POST /companies/{cid}/notifications/link`): роль в боте выводится из веб-роли — владелец и администратор → `admin`, аналитик → `rater`, наблюдатель → `viewer`. При смене роли и удалении api сообщает боту (`notifications/web-role`): личные чаты удалённого отключаются. Роли участников групп без веб-аккаунта назначает администратор («Команда и политики»). Права на запросы к `notifier`: настройки и команда бота — администратор, цели и ретро — аналитик, остальные чтения — любая роль.
