# Проверочное руководство по интерфейсу

Документ для приёмки: **что делает каждая кнопка и откуда взято каждое число на каждом графике**. Написан по коду (`frontend/src/**`, `backend/api/src`, `backend/forecast/src/model.rs`, `backend/planfact`, `backend/ledger`, `backend/services/*`), а не по памяти. Подписи элементов взяты из `frontend/src/i18n/locales/ru.json`. Где элемент ничего не делает или не подключён, это написано прямо («не подключено»). Где поведение выведено из кода, но на живом стенде не проверялось, стоит пометка «по коду».

> Статус: справочник для ручной проверки. Код не менялся. Стенд при написании не был запущен, поэтому цифры раздела «Что должно быть видно на демо» разделены на **выведенные из данных репозитория** (проверяемые) и **эталон владельца** (взят из постановки задачи, сверить на стенде).

### Краткая легенда

* **Роли и права:** `read` (все), `edit` (director, admin, editor), `admin` (director, admin), `manage` (только director). viewer = только `read`.
* **Идентификаторы:** `A-` вход, `G-` экраны доступа, `L-` оболочка, `D-` обзор, `F-` прогноз, `S-` сценарии, `P-` план и факт, `O-` платежи, `T-` операции, `Y-` цели, `H-` журнал, `C-` консультант, `ST-` настройки, `OP-` оператор; виджеты и графики `W-…`.
* **Деньги в API** это копейки строкой; в интерфейсе целые рубли (округление), на графиках рубли с отсечением копеек.
* **Пометки:** «не подключено» (есть в API или коде, нет в интерфейсе или не работает), «по коду» (выведено чтением кода, на стенде не проверялось), «эталон» (значение из постановки владельца), `{cid}` = id компании, `$C` = `$BASE/api/v1/companies/$CID` (см. 0.3).
* **Как проверять число:** взять его из таблицы или графика, затем получить то же из API командой `curl` + `jq` из колонки «Как проверить»; расхождение больше 1 ₽ или в дате это дефект.

## 0. Легенда и общие приёмы проверки

### 0.1 Как читать таблицы

Для каждого экрана две таблицы.

**Таблица 1. Кнопки и элементы управления.** Колонки:

| Колонка | Смысл |
|---|---|
| № | Идентификатор элемента (для отчёта о проверке: `D-03`, `ST-17` и т. д.) |
| Элемент | Название на экране по RU i18n (в «ёлочках»); в скобках тип, если это не кнопка |
| Что делает | Действие на фронтенде |
| API | Метод и путь. `{cid}` = id компании. «клиент» = запроса нет, всё в браузере |
| Роль | Нужное право (см. ниже) и поведение для viewer |
| Ожидаемый результат | Что изменится на экране и в данных |
| Как проверить | Шаги и на что смотреть |
| Ошибки | Типичные отказы (код ошибки API, если есть, и сообщение) |

**Таблица 2. Графики и виджеты.** Колонки: название; что нарисовано (оси, серии, цвета); источник (эндпоинт и поле JSON); формула или откуда число; как проверить (curl и `jq`); типичные ошибки интерпретации.

### 0.2 Роли и права

По `docs/roles.md`. Роли: `director` (Владелец), `admin` (Администратор), `editor` (Аналитик), `viewer` (Наблюдатель).

| Право | Что даёт | director | admin | editor | viewer |
|---|---|:-:|:-:|:-:|:-:|
| **read** | все GET и вычисляющие POST (прогноз, сценарий, backtest, вопрос консультанту, свои токены и чаты) | да | да | да | да |
| **edit** | любые изменения данных: импорт, ожидаемые платежи, категории, налоговый календарь, sync интеграций, применение предложений консультанта, `demo/advance-week`, цели недели | да | да | да | нет |
| **admin** | сотрудники (editor/viewer), приглашения, название компании, Telegram и расписание, отделы, журнал, настройки ФНС / консультанта / режима обновления прогноза | да | да | нет | нет |
| **manage** | администраторы, передача владения, способы входа директора, токены других сотрудников | да | нет | нет | нет |

Интерфейс только скрывает или блокирует кнопки (`app/perms.ts`, `lib/roles.ts`); решает всегда сервер: нарушение даёт `403 forbidden` («Недостаточно прав для этого действия»). У viewer кнопки изменения данных (`useEditGuard`) получают `disabled` и подсказку «Недостаточно прав: для этого действия нужна роль «Аналитик» или выше», над страницей жёлтая полоса «У вас права только на чтение: изменять данные компании нельзя.».

### 0.3 Подготовка: сессия, `curl`, `jq`

Все числа с деньгами в API это **копейки строкой** (`"-1250050"` = −12 500,50 ₽). Даты `YYYY-MM-DD`. Интерфейс округляет до целых рублей (`formatKop`: к ближайшему рублю), графики рисуются в рублях с **отсечением копеек** (`kopToRub`: целочисленное деление на 100), поэтому расхождение между подсказкой графика и таблицей до 1 ₽ нормально.

```bash
BASE=http://localhost:3000                       # шлюз (GATEWAY_PORT)
JAR=$(mktemp)                                    # cookie-файл сессии
# вход демо-директором без пароля (нужен DEMO_LOGIN=1) или обычный POST /auth/login
curl -sS -c "$JAR" -X POST "$BASE/api/v1/auth/demo/login" -H 'content-type: application/json' \
     -d '{"account":"director"}' | tee /tmp/me.json | jq '{email, role, company_id, permissions}'
CID=$(jq -r .company_id /tmp/me.json)
C="$BASE/api/v1/companies/$CID"
api() { curl -sS -b "$JAR" "$@"; }               # GET; для POST добавляйте -X POST -H 'content-type: application/json' -d '...'
```

Если у демо-директора включена 2FA, ответ будет `{"mfa":…}` и сессии не будет: тогда войдите в браузере и скопируйте cookie `session` в `JAR`. Для других ролей: `{"account":"editor"}` (demo-editor@example.com), `{"account":"viewer"}` (demo-viewer@example.com).

Часто нужные запросы (используются ниже по ссылке «см. 0.3»):

```bash
api $C/forecasts/latest | jq '.result | {as_of, horizon, bridge_days, opening_balance, n_paths, model_version}'
api $C/forecasts/latest | jq '.result.risk | {level, shortfall_probability, raw_shortfall_probability, possible_break_date, first_break_date, deficit_given_break_median, max_deficit_p90}'
api $C/forecasts/latest | jq '.result.days | min_by(.p50|tonumber) | {date, p50, p10, p90}'     # точка «Минимальный остаток»
api $C/forecasts/latest | jq '[.result.planned[] | select((.amount|tonumber) > 0) | (.amount|tonumber)] | add / 100'   # «Плановые поступления», ₽
api "$C/plan-fact?days=90" | jq '{as_of, days, missed, items: (.items|length), by_status: (.items|group_by(.status)|map({(.[0].status): length})|add)}'
api $C/expected-events | jq '{total: (.items|length), by_source: (.items|group_by(.source)|map({(.[0].source): length})|add)}'
api "$C/transactions?limit=1" | jq .total
```

### 0.4 Общие правила, действующие на всех экранах

* **Каждое изменение данных повышает ревизию данных** (`data_revision`) в ledger. Следующее чтение `GET …/forecasts/latest` само пересчитывает базовый прогноз с тем же горизонтом (поле `recomputed: true`, плашка «Прогноз пересчитан автоматически»). Плашка «Прогноз устарел» появляется редко: только если автопересчёт не удался.
* **Кэш экрана:** после любой мутации сбрасываются все запросы `['co', companyId, …]` (`useInvalidateAll`), поэтому все экраны обновляются без перезагрузки. Исключения (свои ключи) отмечены в таблицах.
* **Состояния:** «Загрузка данных…» (скелетон), «Не удалось загрузить данные» + «Повторить» (`ErrorState`), пустые состояния. Для проверки ошибок остановите соответствующий сервис (`./run.sh status`).
* **Язык и тема** (RU/EN, светлая/тёмная) хранятся в браузере (`localStorage`), на сервер не уходят.
* **401** в середине работы возвращает на экран входа; **403 `company_banned` / `password_required`** перечитывает `/auth/me`, и поверх приложения показывается экран доступа (раздел 2).

## 14. Панель оператора

Файлы `features/operator/*`; бэкенд `backend/api/src/admin.rs`, сервис `backoffice` (`docs/backoffice.md`). Адрес **`/operator`** (ссылок на неё из интерфейса компаний нет). ### 15.3 Подводные камни при сверке демо (по коду)

* **Событие витрины сопоставляется с операцией только по знаку, дате (±5 дней) и сумме (±30 %), контрагент не сравнивается** (`planfact/src/main.rs`, ветка `key: None`). Поэтому «Плановая оплата от Дистрибьютор-307» (06.08, +102 862,05) вероятнее всего сопоставится с более ранней по порядку операцией 03.08 «Экспедитор-772» +102 216,51 (статус «Оплачено», дата факта 3 авг.), а «Плановая оплата по счёту 872» (12.08, +109 239,50) с 10.08 «Агрохолдинг-884» +91 131,95 (отклонение 16,6 % > 15 % → «Отклонение»), хотя в ленте есть точные платежи Дистрибьютор-307. Комментарий в `seed_showcase.sh` («в план-факте будут «исполнено»») поэтому может не подтвердиться. Проверьте на стенде и зафиксируйте фактический статус.
* **Просроченность события в прогнозе = «дата события ≤ дата данных»**, а не «платёж не пришёл». После шага 5 события 06.08, 10.08 и 12.08 (хотя в «План и факт» они «Оплачено») в «Предстоящих» могут отображаться как «Просрочен», а их суммы повторно входить в прогноз (раздел 17.2, п. 3).
* **Плановые позиции после 20.08 и «Страховой платёж» 05.09** попадают в «План и факт» только когда дата данных их догонит; до этого видны лишь в «Предстоящих» и на графике.
* **Дата «сегодня» сервера** (`chrono::Local::now`) влияет на длину «моста» и на разрешённый диапазон дат ручного события (от «сегодня − 120 дн.» до «сегодня + 730 дн.»): повторный запуск `seed_showcase.sh` после 4.12.2026 не добавит события 06.08–14.08 (`422 invalid_date`).

## 17. Сводка: не подключено и подозрительно

Формат: что, где, чем подтверждается. «Подозрительно» означает расхождение между кодом, подписью на экране и документацией или бесшумную ошибку; решение за владельцем.

### 17.1 Не подключено (есть в API или в коде, но нет в интерфейсе)

1. **Журнал оператора** `GET /api/admin/v1/audit`: в панели `/operator` нет ни экрана, ни кнопки (`features/operator/operatorApi.ts` не содержит вызова).
2. **Переименование чата консультанта**: API `PATCH …/advisor/chats/{id}` принимает `title`, интерфейс отправляет только `model` (`usePatchChat`).
3. **`POST …/advisor/ask`**: хук `useAdvisorAsk` нигде не вызывается (остался от прежней версии).
4. **Включение 2FA для обычного пользователя**: в Настройках нет ни кнопки, ни переключателя; 2FA срабатывает только у учётных записей с `mfa_required` (задаётся CLI auth).
5. **Ввод и редактирование ИНН / ОГРН компании**: поля в Настройках только для чтения; API (`PATCH {cid} {inn,ogrn}`, admin) умеет. См. ST-04.
6. Неиспользуемые ключи i18n (мёртвые строки): `auth.ecp.companyRequired`, `header.account`, `perms.directorOnly`, `common.noDataLower`, `common.noRecords`, `fns.cp.source`, `assistant.rulesBadge`, `assistant.aiBadge`, `assistant.noForecastTitle` / `noForecastText`, `assistant.suggestions.cause|delay|biggest|review|reduce`.
7. Метка вертикальной линии «Дата данных» (`chart.today`) на графиках прогноза никогда не показывается (подпись скрыта, если дата среди первых трёх точек, а график начинается с неё).
8. Комментарий в `TeamPolicies.tsx` («показывается, только когда подключён бот») не соответствует коду: блок виден администратору всегда.

### 17.2 Подозрительно

1. **Подкатегория операции не блокируется для наблюдателя и молча падает** (`TransactionsPage.tsx`, T-07): `disabled` учитывает только `isPending`, ошибка `useSetSubcategory` не выводится. У viewer выбор отправляет запрос, получает 403, на экране ничего не меняется и сообщения нет.
2. **Ретро целей не блокируется для наблюдателя** (`GoalsPage.tsx`, Y-04/Y-05): `POST …/notifications/retro` требует edit, но кнопки и список активны.
3. **Ожидаемые события никогда не закрываются фактом.** В прогнозе событие с датой ≤ даты данных всегда считается просроченным и переносится на `as_of + 1` (`model.rs`, `expand_events`: `overdue = e.date <= as_of`), `ledger` отдаёт все события без сопоставления с операциями. Для уже оплаченных событий это означает «Просрочен» в «Предстоящих», предупреждения `overdue_income` / `overdue_expense` и повторное включение суммы в прогноз. Заметно на демо после шага 5. Подтвердить на стенде.
4. **Журнал показывает коды без перевода** для: `advisor.ask`, `advisor.chat.message`, `advisor.plan.delete`, `advisor.settings`, `advisor.suggestion.apply`, `fns.settings`, `forecast.settings`, `integrations.sync`, `integrations.fns.sync`, `integrations.fns.ens_import`, `transaction.subcategory`, `demo.advance_week`, `notifications.<раздел>.<метод>`. Не журналируются удаление ожидаемого события и смена категории операции (без подкатегории).
5. **Функции ФНС недоступны из интерфейса** для компании без ИНН (демо-компания), а подсказки «Укажите его в реквизитах компании» и «Укажите ИНН в настройках» отсылают к полю, которого нет (п. 17.1.5).
6. **«Способы входа»: кнопка «Удалить» у email** активна, когда есть подпись, но сервер всегда отвечает `409 password_required` (`account_remove_email` безусловно отказывает). Кнопка не должна быть активной.
7. **Сопоставление событий с операциями в «План и факт» без контрагента** (`planfact/src/main.rs`): возможны «ложные» статусы «Оплачено / Отклонение» (раздел 15.3). Подпись «План … (in-sample)» предупреждает только про регулярные платежи.
8. **KPI «Просрочено»** на странице «Платежи» складывает просроченные позиции прогноза и позиции «Не пришло» из план-факта; один платёж может быть посчитан дважды.
9. **Подписи**: карточка «Введено вручную» содержит все события (1С, ЭДО, налоговые); KPI «Плановые поступления» подписан горизонтом, а суммирует «горизонт + мост»; кнопка входа «Редактор» ведёт в роль «Аналитик».

11. **Побочные эффекты «вычисляющих» запросов**: смена горизонта на «Прогнозе» (F-01), «Пересчитать» и «Рассчитать сценарий» доступны наблюдателю, но создают записи прогонов на сервере (сценарий создаёт ещё и новый базовый прогон, который становится `forecasts/latest`).
12. **Ограничение дат ручного события** («сегодня − 120 дней … + 730 дней») нигде не объясняется в форме; ошибка приходит как `422 invalid_date` без перевода (в `apiErrors` ключа нет, показывается серверный текст «Дата вне допустимого диапазона»).
13. **`update_company`**: в комментарии к функции сказано `manage`, фактически требуется `admin` (`docs/roles.md` согласуется с кодом, комментарий устарел). Не влияет на поведение.
14. **Поиск по операциям чувствителен к регистру кириллицы** (`ledger/src/routes.rs`, `list_transactions`): искомая строка приводится к нижнему регистру в Rust (с кириллицей), а сравнивается с `lower(counterparty)` / `lower(purpose)` в SQLite, у которого `lower()` работает только для латиницы (то же написано в комментарии ledger про правила компании). Поэтому «элеватор» не найдёт «ООО «Элеватор-242»» (заглавная «Э» в базе остаётся заглавной), а «леватор» найдёт. Сортировка по контрагенту `COLLATE NOCASE` тоже без кириллицы. Проверка: `api -G "$C/transactions" --data-urlencode "q=элеватор" -d limit=1 | jq .total` против `q=леватор`. Подтвердить на стенде.
