# Архитектура ML

Документ описывает, как устроена аналитика, что из неё уже работает и проверено, а что запланировано. Критерии кейса «Центр Инвест»: качество прогноза и его проверка, заблаговременность и корректность выявления разрывов, вклад дополнительных источников, граничные случаи, сравнение подходов.

## 1. Схема

```mermaid
flowchart LR
  S[выписка / 1С / ЭДО / банк / ручной ввод] --> P[parser: правила + taxonomy]
  P -->|13 категорий ledger + подкатегория, группа, doc_no/doc_date, is_rescue| L[(ledger)]
  L --> F[forecast, Rust: champion]
  subgraph F[forecast, Rust]
    E1[слой 1: известные события] --> MC
    E2[слой 2: регулярные потоки] --> MC
    E3[слой 3: остаточный поток] --> MC[Монте-Карло: P10/P50/P90, P(остаток<0)]
    MC --> CAL[калибровка вероятности]
  end
  F --> PF[planfact] --> F
  F --> N[notifier: алерты, отчёты, цели]
  F --> H[Hermes: объясняет, советует; данные маскируются]
  LAB[ml/: единый бэктест, challenger-модели] -. сравнение и выбор .-> F
```

Три принципа:
1. **Цифры считает модель, а не LLM.** Дату, вероятность и сумму разрыва даёт Монте-Карло с калибровкой. Hermes только объясняет и советует (`notifier/advisor.py`), цифр не меняет.
2. **Слои вместо одной модели.** Остаток = начальный остаток + известные события (счета, налоги, ручной ввод) + регулярные платежи + остаточный поток. Каждый разрыв раскладывается на причины, а новый источник данных попадает в первый слой без переобучения.
3. **Сначала измерили, потом включили.** Любое усложнение проходит единый бэктест (раздел 5); если выигрыша нет, оно остаётся выключенным.

## 2. Данные и разметка

Парсер (`backend/services/parser`) возвращает для каждой операции прежние поля и новые признаки для ML:

| Поле | Что это |
|---|---|
| `category` | одна из 13 категорий ledger (как раньше, интерфейс и прогноз не менялись) |
| `subcategory`, `group` | 28 подкатегорий в 10 фиксированных группах, правила в `parser/categories.yaml`, первое совпадение побеждает (`taxonomy.py`; таксономия из проекта «ЦИ1», ветка `gleb`) |
| `doc_no`, `doc_date` | номер и дата документа-основания («по УПД № 279 от 19.08.2024») |
| `is_rescue` | поступление собственных денег (`own_transfer_in`, `founder_loan_in`), без которого остаток дня ушёл бы в минус |

Режим налогообложения выводится по выписке (`regime.py`: НДС в оплатах, ритм ЕНП, доля налогов), владелец подтверждает. Модель на «хвост» нераспознанных операций (`tail.py`: TF-IDF по символьным n-граммам и логистическая регрессия, обучение по тенанту, порог 0,55, минимум 200 примеров) подключена к ledger: при загрузке выписки операции, которых не распознали правила (метод `fallback`), размечаются моделью компании, если в ledger уже есть 200+ размеченных операций; в `transactions` добавлены `subcategory`, `grp`, `method` (`rule | tail | tenant_rule | manual | fallback`), уверенность лежит в `category_conf`. Правка подкатегории в интерфейсе запоминается как правило компании по контрагенту (`tenant_rules`), действует сразу на его остальные неправленные операции и на следующие выписки; она же служит меткой для обучения. Образ `parser` ставит scikit-learn (группа `tail`), без него импорт идёт на правилах, как раньше.

**Два слоя разметки в парсере.** Ветка `testing` принесла свою реализацию тех же идей без sklearn: `categorize.py` + `gleb_rules.py` (правила по назначению и по имени контрагента, метод в `category_method`), `tail_model.py` (наивный байесовский классификатор на чистом Python, учится на самой выписке и включается от 100 размеченных операций в направлении), `tax_regime.py` (подсказка режима в `stats.tax_regime_guess`), разбор формата 1С. Они остаются и работают на этапе разбора файла: дают 13 категорий, `category_method`, `stats.rule_coverage`, `stats.ml_categorized`. Таксономия `taxonomy.py` добавляет подкатегорию, группу, документ-основание и флаг `is_rescue` (признак ставится, если сработал любой из двух расчётов). Модель на хвост по истории компании (`tail.py`, TF-IDF + логистическая регрессия) работает уже в ledger: она видит всю историю, а не одну выписку, и переразмечает только строки, у которых правила подкатегорию не нашли (`method=fallback`); правила компании (`tenant_rules`) и ручные правки сильнее обеих моделей. Этапы не конфликтуют: первый отвечает за категорию в предпросмотре импорта, второй — за подкатегорию в ledger.

**Проверено на датасете организаторов** (222 399 операций после удаления 21 дубля, 150 компаний):

| | |
|---|---|
| не распознано правилами (`other_in/out`) | 0,29 % |
| совпадение с прежним 13-категорийным классификатором (по схеме ledger) | 98,8 % |
| операций с документом-основанием (все направления) | 64 626 |
| «спасательных» поступлений собственных денег | 482 операции у 73 компаний |

«Спасательные» поступления важны для оценки. Владелец закрывает дыры своими деньгами в тот же день, поэтому остаток в выписке не уходит в минус, и разрыв, о котором надо было предупредить, виден только после вычитания этого поступления. Прогноз строится «как если бы владелец не вмешался» (`transfers` и так не входят в остаточный поток), а разрывы в оценке размечаются двумя способами: `raw` (остаток действительно < 0) и `adjusted` (без спасательных поступлений).

## 3. Ядро прогноза (Rust, `backend/forecast`)

Работает в проде и остаётся основным: календарь РФ, регулярности (двухуровневый ключ «контрагент + основа назначения»), остаточный поток блочным бутстрепом по неделям, снятие дрейфа и возврат к среднему, сценарии «что если», пропуски выписки, логистическая калибровка вероятности разрыва. Метрики и история улучшений: `docs/forecast_evaluation.md` (142 компании, 229 окон разрыва; Brier 0,0125 после калибровки).

Добавлено: разметка разрыва с учётом спасательных поступлений (`rescue_inflows`, `adjusted_gap`, итоговая строка в `eval`); задержки оплат по Каплану–Мейеру (`delays.rs`); драйверы разрыва и уровни `warning/critical`. Всё собрано и проверено `cargo test --workspace` (в `forecast` 30 тестов, в `ledger` 22).

**Задержки по Каплану–Мейеру** (`DelayModel`, `Params.km_delays`, по умолчанию включено; `eval --no-km` — прежняя таблица). Наблюдения: опоздание регулярных поступлений контрагента относительно самого раннего платежа якоря (оплата наступила) и просроченные ожидаемые поступления (цензурированы: ждём уже `age` рабочих дней). Кривая контрагента сжимается к общей с весом `n/(n+5)`; для просроченного платежа задержка выбирается условно на «не заплатил к возрасту `age`», за пределами наблюдений — хвост до 7 дней. Применяется к ожидаемым событиям-поступлениям (счета) и к просроченным регулярным поступлениям; при менее чем 8 наблюдениях остаётся прежняя таблица. `forecast_runs` хранит `seed` и версию модели (`recurring-bootstrap/3`), расчёт детерминирован.

**Драйверы и уровни.** У предупреждения `cash_gap` появились `tier` (`critical` — вероятность разрыва ≥ 50 % или медианная траектория уходит ниже нуля, иначе `warning`) и `drivers`: до 5 статей с долей вклада в давление на остаток (расходы до даты разрыва и просроченные поступления), сумма долей = 1 по всем давящим статьям.

**Не сделано:** инкрементальный кэш `Fitted` по `data_revision`. Один прогноз занимает ≈0,6 с на 222 тыс. операций, весь бэктест 142 компаний ≈6 с, а честная инвалидация кэша (события, сценарий, настройки, мост до сегодняшнего дня) без возможности измерить выигрыш на реальной нагрузке — риск ошибок устаревших прогнозов; делать, когда прогноз станет узким местом.

## 4. Challenger-модели (`ml/lab`)

Общий интерфейс `Forecaster` (`fit(ряд)`, `sample(дни, n)`), каждая модель даёт траектории остаточного потока в тот же Монте-Карло. В реестре: плоский остаток, повтор прошлой недели, бутстреп по дню недели, блочный бутстреп (аналог Rust-ядра), **ETS** и **Theta** (`statsforecast`, ряд по рабочим дням, интервал 80 % → нормальное приближение), **градиентный бустинг с квантильной потерей** (глобальная модель на все компании, нормировка на недельный оборот, календарные признаки: день недели и месяца, дни до ЕНП 28-го, рабочий день, конец месяца, уровни последних 5/20/60 рабочих дней; обучение только на данных до границы теста и leave-company-out по 5 фолдам; LightGBM, если есть, иначе HistGradientBoosting), **Chronos-Bolt** (zero-shot, только эксперимент). Слои: регулярные платежи (`recurring`), счета (реконструкция по номерам документов), налоговый календарь (ЕНП 28-го, сумма по истории).

## 5. Результаты единого бэктеста

Условия: 28 компаний (равномерная выборка из 150, 2 отсеяны по длине истории), до 8 срезов на компанию с шагом 14 дней в тестовом периоде с 01.11.2025, горизонт 30 дней, 200 траекторий. NMAE — MAE остатка к недельному обороту компании в %. Остаток сравнивается с фактическим без спасательных поступлений. Доверительные интервалы получены бутстрепом по компаниям. Полный отчёт: `ml/reports/backtest-2026-10-24.md` и `.json` (с sha256 данных).

|---|---|---|---|---|---|---|---|---|
| плоский остаток | 54,2 | 99,4 [80,2; 123,2] | 0,005 | 0,344 | — | 0,00 | — | 0,174 |
| бутстреп по дню недели | 58,0 | 100,7 [82,7; 120,7] | 0,795 | 0,275 | 0,41 | 0,83 | 15 | 0,122 |
| ETS | 54,4 | 102,6 [85,9; 129,7] | 0,928 | 0,251 | 0,53 | 0,91 | 15 | **0,093** |

Как это читать честно:
- **Точечная ошибка остатка не различает подходы.** Доверительные интервалы NMAE на 30 дней перекрываются у плоской модели, обоих бутстрепов, ETS, бустинга и Chronos; заметно хуже только «повтор недели» и, в меньшей степени, Theta. Остатки близки к случайному блужданию, поэтому «плоская» модель сильна; об этом же говорит `forecast_evaluation.md`.
- **Различаются вероятностные метрики.** «Плоская» модель не видит ни одного разрыва и не имеет интервалов. ETS, бустинг и Chronos дают лучшую квантильную ошибку (pinball 0,238–0,251 против 0,275 у бутстрепа); ETS лучше всех по Brier (0,093) и полноте (0,91) при заблаговременности 15 дней; бустинг лучше на 7 днях, но пропускает половину разрывов.
- **Сравнивать с цифрами `forecast_evaluation.md` напрямую нельзя:** там 142 компании, весь период и разметка `raw`; здесь 28 компаний, отложенный период и разметка `adjusted` (остаток минус спасательные поступления), поэтому ошибки выше.
- **Слой счетов не улучшает точность, налоговый слой её ухудшает** на этой выборке (слой счетов лишь немного улучшает калибровку: ECE 0,062 против 0,081). Реконструкция счетов по назначениям платежей — суррогат (сумма берётся из фактических платежей, что слегка завышает знание), и вывод о ценности настоящих счетов из 1С/ЭДО она не даёт. Это нужно проверять на реальных счетах.
- Выборка небольшая (≈220 срезов на подход, десятки окон с разрывом): интервалы широкие, победителя по одной метрике называть рано.

**Решение:** challenger не заменяет ядро. Ядро остаётся основным, а ETS и бустинг — кандидаты для остаточного слоя; подключать `ml-serving` имеет смысл после проверки на полном наборе из 142 компаний и с калибровкой вероятности поверх (как в Rust-ядре), потому что именно калибровка дала там основной выигрыш (Brier 0,082 → 0,0145).

## 7. Запуск

```bash
# окружение лаборатории (в образы сервисов не попадает)
cd backend/services && uv sync --group ml && cd ../..
export MOCK_DATASET_DIR="<каталог cashflow_dataset_participants>"
python -m ml.backtest.run --companies 30 --cutoffs 8            # отчёт в ml/reports/
python -m ml.backtest.run --variants naive_flat,weekday_bootstrap,ets,gb_quantile,chronos
python -m ml.backtest.gate ml/reports                           # гейт качества
pytest ml/tests backend/services/tests                          # тесты
```
Датасет только читается. Chronos при первом запуске скачивает веса модели (`amazon/chronos-bolt-tiny`, переменная `CHRONOS_MODEL`) и требует `chronos-forecasting` и `torch`; без них вариант `chronos` выключается.

## 8. Ограничения
- Данные синтетические: «спасательные» поступления и поведение владельца — свойства генератора, на реальных данных банка калибровку и разметку надо переобучать.
- Остаточные модели сэмплируют дни независимо, поэтому дисперсия остатка за месяц недооценена; это же причина узкой полосы на коротких горизонтах.
- Бустинг в бэктесте обучен на HistGradientBoosting (на машине разработки не было OpenMP для LightGBM); в Docker/Linux подхватится LightGBM.
- Производственный календарь для будущих дат упрощён (выходные и фиксированные праздники): перед продом заменить на официальный.
