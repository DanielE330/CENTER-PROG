# Подключение почты (SMTP)

Письма отправляет сервис `notify` (см. [notify.md](notify.md)). По умолчанию все письма ловит Mailpit (http://localhost:8025, виден только с этой машины), наружу ничего не уходит. Чтобы письма доходили до людей, задайте реальный SMTP-сервер в `infra/.env` и перезапустите `notify`:

```
docker compose -f infra/docker-compose.yml up -d notify
```

## Переменные

| Переменная | Что это | По умолчанию |
|---|---|---|
| `SMTP_HOST` | адрес SMTP-сервера | пусто = Mailpit |
| `SMTP_PORT` | порт | по режиму: 465 ssl, 587 starttls; у Mailpit 1025 |
| `SMTP_SECURITY` | `ssl` (TLS с первого байта, порт 465), `starttls` (порт 587), `none` | по порту: 465 = ssl, 587 = starttls, свой хост без порта = starttls:587 |
| `SMTP_USER`, `SMTP_PASSWORD` | вход; пароль приложения, не пароль от ящика | пусто = без входа |
| `MAIL_FROM` | отправитель, `noreply@example.ru` или `Центр Прогнозирования <noreply@example.ru>` | адрес `SMTP_USER` |
| `SMTP_HELO` | имя в EHLO | хост из `PUBLIC_URL`, иначе домен отправителя, иначе `localhost` |
| `SMTP_TLS_VERIFY` | `0` отключает проверку сертификата | `1` |
| `SMTP_CA_FILE` | корневой сертификат своего сервера (путь внутри контейнера) | системные |
| `SMTP_TIMEOUT_SECONDS` | таймаут соединения и ответа | 15 |
| `SMTP_MAX_PER_MINUTE` | лимит скорости, 0 = без лимита | 30 |
| `PUBLIC_URL` | адрес сайта для ссылок в письмах | `http://localhost:3000` |

Прежние `SMTP_FROM`, `SMTP_SSL=1`, `SMTP_STARTTLS=1` тоже понимаются.

Три правила, на которых чаще всего ломается:

1. **Отправитель должен быть адресом того же ящика.** Gmail подменит чужой `From` на ваш адрес, Яндекс и Mail.ru отклонят письмо ответом `553`/`550`. Поэтому без `MAIL_FROM` отправителем становится `SMTP_USER`. Адрес по умолчанию `noreply@centr-prognoz.local` годится только для Mailpit.
2. **Пароль приложения, не пароль от ящика**, и только латиница, цифры и знаки (ASCII). Если в пароле есть `$` или `#`, возьмите его в одинарные кавычки: `SMTP_PASSWORD='pa$s#word'`.
3. **Комментарии в `.env` пишите на отдельной строке.** Docker Compose читает `SMTP_HOST=   # пусто` как значение «# пусто». `notify` такие значения игнорирует, но остальные сервисы нет.

## Gmail

1. В аккаунте Google включите двухэтапную аутентификацию, затем на странице «Пароли приложений» создайте пароль (16 символов).
2. В `infra/.env`:

```
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USER=you@gmail.com
SMTP_PASSWORD=abcdefghijklmnop
```

`MAIL_FROM` не задавайте. Лимит Gmail около 500 писем в сутки.

## Яндекс 360

1. В почте: Настройки -> Почтовые программы -> разрешите доступ по протоколу IMAP/SMTP, затем в «Безопасность» создайте пароль приложения (тип «Почта»).
2. Адрес должен принадлежать вашему домену в Яндекс 360 или быть `@yandex.ru`.

```
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_SECURITY=ssl
SMTP_USER=noreply@example.ru
SMTP_PASSWORD=<пароль приложения>
```

## Mail.ru

Настройки -> Безопасность -> «Пароли для внешних приложений», тип доступа «Почтовые клиенты» (SMTP).

```
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SECURITY=ssl
SMTP_USER=you@mail.ru
SMTP_PASSWORD=<пароль для внешнего приложения>
```

## Свой сервер (Postfix, Exim и т. п.)

```
SMTP_HOST=mail.example.ru
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USER=noreply@example.ru
SMTP_PASSWORD=<пароль>
SMTP_HELO=forecast.example.ru
```

- С настоящим сертификатом (Let's Encrypt и т. п.) ничего больше не нужно.
- С самоподписанным или корпоративным: смонтируйте корневой сертификат в контейнер и укажите путь в `SMTP_CA_FILE` (например, через `docker-compose.override.yml`: `volumes: ["./ca.pem:/ca.pem:ro"]` для `notify`). Крайний вариант: `SMTP_TLS_VERIFY=0`.
- Чтобы письма не попадали в спам, у домена отправителя должны быть SPF, DKIM и обратная запись PTR у IP сервера. Проверить это изнутри платформы нельзя.
- Сервер в той же сети docker без шифрования: `SMTP_SECURITY=none`, `SMTP_PORT=25`; пароль в этом режиме уходит открытым текстом.

## Mailpit (по умолчанию)

Оставьте `SMTP_HOST` пустым. Письма смотрите на http://localhost:8025. Подходит для разработки и демо; на реальные адреса ничего не уходит.

## Как проверить

Проверка соединения, шифрования, входа и отправителя **без отправки письма**:

```
docker compose -f infra/docker-compose.yml exec notify python -m notify.check
```

С тестовым письмом на ваш адрес (после успешной проверки):

```
docker compose -f infra/docker-compose.yml exec notify python -m notify.check --to you@example.ru
```

Код выхода 0 — всё в порядке, 1 — ошибка. Вывод: на каком шаге остановились (соединение, EHLO, STARTTLS, вход, отправитель), класс ошибки и что делать. Пароль не печатается.

То же по HTTP из внутренней сети: `GET http://notify:8014/internal/v1/smtp/check` отвечает `{ok, stage, error_class, hint, detail, host, port, security, sender, user_set, warnings}`. Состояние очереди: `GET /internal/v1/outbox` (`queued`, `sent`, `failed`, `errors` по классам, `last_error`).

В кнопке «Отправить тестовое письмо» (Настройки) письмо проходит весь путь: api -> notify -> очередь -> SMTP. Если оно не пришло, смотрите `docker compose -f infra/docker-compose.yml logs notify`: при старте там строка `notify: smtp host:port security=… auth=… helo=…`, при сбоях `message N not sent (класс код), now queued|failed`. Адресов, паролей и текстов писем в журнале нет.

## Ошибки и что они значат

| Класс | Что произошло | Что делать |
|---|---|---|
| `config` | `SMTP_*` заданы неверно (порт не число, пароль без логина, `MAIL_FROM` без `@`, не-ASCII пароль) | исправить по тексту подсказки; пока настройки неверны, письма ждут в очереди |
| `dns` | имя `SMTP_HOST` не находится | проверить написание хоста; у контейнера `notify` должна быть сеть `mail` с выходом наружу |
| `connect_refused` | на хосте и порту никто не слушает | проверить `SMTP_HOST`, `SMTP_PORT` |
| `timeout` | сервер не ответил за `SMTP_TIMEOUT_SECONDS` | исходящие порты 25/465/587 закрыты у хостинга или файрволом, либо неверный режим |
| `tls_mismatch` | порт 465 с `starttls` или `none` | на 465 нужен `SMTP_SECURITY=ssl` |
| `tls` | ошибка TLS: чаще всего `ssl` на порту 587 | на 587 нужен `starttls` |
| `tls_cert` | сертификат не прошёл проверку | `SMTP_CA_FILE` или (крайне) `SMTP_TLS_VERIFY=0`; для публичных серверов проверьте, что `SMTP_HOST` совпадает с именем в сертификате |
| `starttls_unsupported` | сервер не умеет STARTTLS на этом порту | порт 465 + `ssl`, либо `none` для внутреннего сервера |
| `auth_unsupported` | сервер не предлагает вход | неверный порт или режим; на 587 вход доступен только после STARTTLS |
| `auth_failed` (535) | логин или пароль отклонены | пароль приложения, а не пароль ящика; у Gmail включена 2FA; у Яндекса включён доступ по SMTP |
| `sender_refused` (553, 550) | адрес отправителя чужой | `MAIL_FROM` равен `SMTP_USER` или не задан |
| `recipient_refused` (550, 553) | получателя нет или ящик закрыт | письмо сразу получает статус `failed`, повторов нет |
| `unicode_address` | кириллица до `@` (`почта@firm.ru`), сервер без SMTPUTF8 | письмо сразу `failed`; домен на кириллице (`user@пример.рф`) отправляется нормально, он преобразуется в punycode |
| `message_rejected` (554) | сервер счёл само письмо спамом | письмо `failed`; проверить SPF/DKIM домена отправителя |
| `rate_limited` (421, 450, 451, 452) | временный отказ: лимит, серый список | повторится сам |
| `disconnected` | сервер оборвал соединение | неверный режим для порта, блокировка по IP после частых неудачных входов |

## Как работает доставка при сбоях

- Письмо сначала записывается в очередь (SQLite, том `notify-data`), и пользователь получает ответ сразу: недоступный SMTP не замедляет регистрацию, приглашения и сброс пароля. Если `notify` совсем недоступен, `api` отвечает по-прежнему, а сайт сообщает, что письмо не отправлено (ссылку приглашения или пароль сотрудника в этом случае показывает сайт).
- Временные сбои повторяются через 1, 5, 30 и 120 минут, затем статус `failed`. Пока сервер недоступен для всех (связь, TLS, вход, отправитель), за один проход очереди пробуется одно письмо: сервер не заваливается запросами, а неверный пароль не вызывает блокировку аккаунта.
- Постоянные ошибки письма (получателя нет, письмо отклонено) сразу дают `failed`, без повторов.
- Один и тот же `dedup_key` второго письма не создаёт; параллельные проходы очереди не отправляют письмо дважды.
- Лимит скорости `SMTP_MAX_PER_MINUTE`: остальные письма уходят на следующих проходах.
- После исправления настроек верните сутки `failed` назад в очередь: `curl -X POST http://notify:8014/internal/v1/outbox/requeue` (из контейнера `api` или `notify`: `python -c "import urllib.request as u; print(u.urlopen(u.Request('http://127.0.0.1:8014/internal/v1/outbox/requeue', method='POST')).read())"`). Письма с вложениями (рассылки notifier) не возвращаются, их пришлёт расписание.
